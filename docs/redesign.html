01The claim

Every other project tool is a database beside your repository. This one is a query over it.

You asked me to look at the current system, survey what exists in project management, and restate your vision properly. Here is the restatement, and it is sharper than the brief you gave me.

You described adding AI features to a project management tool: a VS Code extension, separate AI and human tracking, a CodeRabbit-style reviewer, an ideation stage in front and an architecture stage after it. Every one of those is right. But framed as features they undersell what you are actually building, and they will get built in the wrong order.

What you are describing is not a project tool with AI in it. It is a manufacturing pipeline for software in which the scarce input has changed. Boards, sprints, story points, velocity, capacity planning and resource-levelled Gantt charts are all machinery for rationing a scarce supply of implementation. That supply is no longer scarce. What is scarce now is deciding what to build, specifying it so precisely that a machine cannot misread it, and believing the result.

So the queue moved. It used to form in front of the developer. It now forms in front of the reviewer — and every tool on the market still draws its widest column in the old place.

Your repository already says this. The Flow phase of docs/prd.md opens with: “AI made generation cheap and review expensive, so work accumulates in front of the reviewer. Show that, and put a valve on it.” That is the sharpest sentence in this whole analysis, and it is currently the goal of one phase out of eight. It should be the thesis of the product.
02What actuallychanged

Every tool encodes a guess about where the bottleneck is

You can read a project tool's assumption straight off what it spends its complexity on. Jira spends it on a workflow engine and a permission scheme, because it assumes the problem is coordinating many people and enforcing process. Linear spends it on latency and triage, because it assumes the problem is the tool getting in a good team's way. Basecamp spends it on appetite and betting, because it assumes the problem is scope creep against fixed time. MS Project spends it on resource levelling, because it assumes the problem is scheduling scarce labour.

All four assumptions share a premise: implementation capacity is finite and must be allocated. Story points size the demand. Velocity measures the supply. Sprint commitment matches them. Burndown reports the variance. Capacity planning forecasts next quarter. WIP limits protect the developer column.

When one well-specified feature becomes a plausible implementation in minutes, and twenty of them can run at once, that entire apparatus is measuring a resource that is no longer the constraint. It does not become wrong so much as irrelevant — a fuel gauge on an electric car.

What stayed scarce

  • Deciding what to build. Entirely human, still slow, and now proportionally the largest cost.
  • Specifying it unambiguously. Partly automatable — an agent drafts a good first pass — but the judgement about what “done” means is not.
  • Believing the output. Review, verification, trust. This is the new bottleneck and almost nothing is built for it.
  • Absorbing the consequences. Twenty parallel changes landing in one codebase is an integration problem no board models.

Which gives the design rule that everything below follows from: the tool's job is to make specification cheap and verification cheap, and to be honest about where humans are the queue.

04Your vision,restated

Five stages, each with a typed artifact and a gate that can refuse

You described ideation, then architecture and schemas, then development tooling. That sequence is right. What makes it a system rather than a set of screens is two properties, and both of them you have already proven once in this codebase.

First: each stage produces a machine-readable artifact that lives in the repository. Not a Jira field, not a Confluence page — a file an agent can read and write and a human can review in a diff. You have already done this for the feature list: docs/prd.md is a document people read, and the app splices only the ranges it owns.

Second: each transition is a gate that can refuse. Not a warning, not a checklist — a refusal, with a reason, that names what would satisfy it. You have already done this twice: a full column refuses task start, and a failing Verify: command unticks criteria the repository just declined to agree with.

Generalise those two properties across all five stages and you have the whole product.

The one-line version

Agents fill the stages. Humans open the gates.

That is the division of labour the whole product should express. It is why “assign this ticket to an AI” is the wrong primitive — it puts the agent in the human's slot instead of giving it its own. And it is why a gate that cannot refuse is worthless: if the only thing standing between a generated spec and generated code is another generation, you have built a machine for producing confident nonsense at scale.

05Two economies

A person and an agent are not the same kind of worker

You asked to “track each progress of AI and human separately”. That is not a reporting preference — it is the load-bearing primitive, because the two lanes obey different physics and any number averaged across them is meaningless.

Five measurements that only this design can produce

All of these fold out of the event log and the provenance ledger. None of them exists in any tool today, because no tool has a record of who wrote which line.

Attempts
Runs per accepted change. Three agent runs to land one feature is the true cost, and it is invisible if you only count the merge.
Survival
Fraction of agent-written lines that reach merge unmodified by a person. The single best quality signal available, and the honest replacement for “percentage of AI code”.
Revision
How deeply a human rewrote agent output — a touch-up versus a rewrite. Volume says the agent contributed; depth says whether it helped.
Spec defect
Runs that failed because the specification was ambiguous, not because the agent was poor. This is the number that tells you where to invest, and it is the one nobody measures.
Wait
Time work spends in front of a person — decision latency plus review queue. On a project of this shape it is most of the calendar.
Design rule. Never average across lanes, and never publish a leaderboard of agent volume. Volume is trivially gameable by an agent and rewards exactly the wrong behaviour. Publish survival, which is not.
06Five load-bearingmechanisms

The parts that make it more than a nicer board

Each of these is a mechanism rather than a screen, and each has a property no competitor can copy without rebuilding their foundation.

A

The provenance ledger

The problem. Git records who committed, never who wrote. In the normal case a person commits an agent's work, so git blame actively lies. Every “percentage of AI-written code” figure on the market is inferred from commit-size heuristics, IDE telemetry sampling or suggestion-acceptance rates. All of it is soft, and all of it is gameable.

What you have that nobody else does. lib/project/ingest.ts already normalises harness hooks onto the OpenTelemetry GenAI conventions and captures, per tool call, the paths actually written — tied to a run whose actor.kind is human or agent and whose model and harness are known. That is a record, not an inference. The comment in that file already makes the argument: “a report is a claim and a hook is a record.”

The extension. Capture byte ranges, not just paths. An Edit hook payload carries the old and new strings; a Write carries the whole file. From that you maintain, per file, a line-to-run map — rebased forward on every subsequent edit the way a blame tree is. The result: for any line in the working tree you can name the run that wrote it, the model, the task, the criterion it claimed to satisfy, and whether a human has since revised it.

Lives in
.project-cache/provenance/ — derived and regenerable from the log, so your rule holds: deleting the cache may only ever change latency, never an answer.
Honest limit
Exact for edits made through an instrumented harness. A human editing in vim outside the harness falls back to blame-based inference, and must be labelled as inferred in every surface. A provenance system that hides its own uncertainty is worse than none.
Unlocks
The VS Code gutter, both AI-versus-human diffs, and all five measurements above. This is why it is phase one.
B

The gate, as an abstraction

You have two gates and they are hard-coded. Promote the idea: a gate is a named predicate on a stage transition that returns a refusal, a reason, and — the part that matters — what would satisfy it.

  • have  A full column refuses task start, naming itself and the numbers.
  • have  A failing Verify: command unticks the criteria it refused.
  • new  Falsifiability — a feature cannot leave Specification while a criterion is unfalsifiable. “Checkout should be fast” is refused; “p95 under 400ms, proven by npm run bench:checkout” passes.
  • new  Design completeness — a feature cannot enter Construction until the components it touches exist in the catalogue and any schema change has a migration.
  • new  Merge — the composite: criteria proven, no unresolved high finding, no new drift, no boundary violation.
The rule that keeps gates from becoming bureaucracy: every refusal must name the smallest thing that would turn it into a yes. A gate that only says no is process; a gate that says “no, and here is the one line that would fix it” is a tool. Where the fix is mechanical, offer to make it.
C

The reviewer that reads the specification

You asked for “an AI review system like CodeRabbit”. Build something they structurally cannot: a reviewer that knows what the change was supposed to do. CodeRabbit, Greptile, Bugbot and Copilot review all read a diff and apply general good taste, because nothing in their pipeline connects a pull request to acceptance criteria. Your lib/project/review.ts already assembles a packet containing the criteria, their check results, the owning components and the reading order. That packet is the moat.

Three tiers, cheapest first — which is also the noise architecture:

Tier 0
Deterministic, no model. Grounding (exists — a finding off the diff is dropped before anyone sees it), architecture drift, boundary violations, failing verify, a schema change with no migration. Zero false positives by construction, which is why it is a floor rather than a preference.
Tier 1
Specification conformance. For each criterion this change claims: does the diff implement it, and if not, which one does it miss? A finding here can untick a criterion, exactly as a failing verify does. This is the differentiated tier and nobody has it.
Tier 2
Craft. Bugs, security, performance. Commodity — match the field, do not try to beat it. Run inside the component boundary, ground every finding, and cap the output.

Budget the review's own attention cost. A review that emits forty comments costs more attention than it saves, which is the well-documented failure of this whole product category. Cap findings per change, rank by severity × blast radius, and put the remainder behind a “not shown” list rather than in the reader's face. The reviewer needs a token budget too — a reviewer that costs more than the work it reviewed is a net loss, and yours can enforce that because runs already have budgets.

Learn in the open. A dismissed finding is an event. Suppression patterns accumulate per component and are stored in .project, where they show up in a diff and can be argued with in code review — unlike the opaque “learnings” competitors accumulate on their own servers.

D

Drift, generalised — this is your architecture-and-schemas stage

You already do the hard version once: lib/project/deps.ts diffs the architecture canvas against the real import graph, and reports coupling that exists and is not drawn. That is an instance of a general mechanism — a drawn claim, checked against what the code actually does — and it is what makes a design stage worth having rather than a folder of stale pictures.

Three more instances, all the same shape:

  • Schema drift. The ER diagram against prisma/schema.prisma, the SQL DDL, or the migration directory. You already parse both formats in lib/arch/import/ — you import one way and never compare back. Closing that loop is a small amount of code for the largest single piece of the stage you asked for.
  • Contract drift. The API surface drawn on the canvas against the actual route handlers, exported types or OpenAPI document. Agents change contracts casually; this is the check that catches it.
  • Ownership drift. Declared Paths: against the files that exist. coverage and catalogWarnings in component.ts already compute most of this — surface unclaimed source as drift, because unowned code is where agent output goes to rot.
This is the honest answer to “we should have system architecture and schemas before development begins”. Documented architecture decays. Checked architecture does not, and the check is the whole product difference.
E

The critical path of waiting — your Gantt, made honest

You asked for Gantt. Gantt is two things bolted together, and they have aged very differently. Its dependency graph is genuinely valuable and you should build it. Its durations and resource levelling are fiction when the implementation lane is elastic — you cannot schedule a resource you can buy more of at will.

So: model dependencies between features explicitly (a Requires: line in the PRD, parsed like Paths: and Verify: already are), compute the critical path — but weight the edges by waiting, not by working. Decision latency. Review queue depth. Time spent refused at a gate. Time blocked on a person.

What you get is a chart of where the project is actually stuck, which on a team using agents is nearly always a human decision or a review backlog. That is a chart no other tool draws, and it is the legitimate successor to the Gantt chart rather than a nostalgic copy of one. Your next command already ranks individual work by age weighted by blast radius; this is that same idea at project scale.

And the honest gaps against the vision

  • missing  No ideation stage at all. The PRD begins already written. There is nowhere for an idea to live before it is a feature.
  • missing  Nothing produces findings. report_findings accepts them and ground() filters them, but no reviewer generates them. The pipe is laid and empty.
  • partial  The design stage has drawings but no gate. Nothing stops a task starting before its component exists or its schema is drawn, and import_schema is one-way.
  • partial  Provenance stops at the file. Runs record which files they touched, not which lines. Everything AI-versus-human depends on closing that.
  • missing  No dependency model. No feature blocks another, so there is no critical path to compute.
  • missing  No editor surface. Everything is a browser tab or a terminal, which is not where the work happens.
08The editorsurface

The extension is a second client, not a second system

Because the store is files in the repository, the extension reads .project, .project-log/ and docs/prd.md directly and shells out to the existing CLI for anything heavy. No server, no sync, no second source of truth. This is the payoff of a decision you already made.

The headline: three diffs git cannot give you

Register a TextDocumentContentProvider on a virtual scheme — companion-run: — that reconstructs file state from the event log, then hand it to the built-in vscode.diff. That yields diffs no git command can produce, because a run is not a commit:

  • Since this run started. What the agent changed in this session, whether or not it has been committed.
  • Agent-only. The working tree with human-attributed hunks removed.
  • Mine-only. The inverse — what you changed, with the agent's contribution subtracted out. This is the one people will actually open every day.

Limits worth designing around, not discovering later

Webviews are isolated — everything crosses a postMessage boundary, so the React Flow canvas can be reused but not simply imported. The extension host is single-threaded and shared with every other extension, so drift computation and provenance folding must go out to the CLI as a subprocess rather than run inline; a slow extension host is the most common reason an extension gets uninstalled. There is no arbitrary gutter UI beyond decorations and a fixed icon slot. Comment threads are ephemeral unless you persist them — you already do, in .project. And web extensions on vscode.dev have no filesystem access at all, so this is desktop-first by construction; say so up front rather than half-supporting it.

09What to refuse

The conventions worth deliberately not having

A tool is defined as much by what it declines to model. Each refusal below should be a stated position, not an omission — and several of them are already the position this codebase takes.

story pointsSizing a task by how long a human would take, when a human is not the one doing it. Use appetite — fixed time, variable scope — which survives the change.
velocityThroughput averaged across two lanes with different physics. The number is arithmetically valid and means nothing.
burndownMeasures adherence to a plan rather than the health of a system. A cumulative flow diagram over the event log answers the same question honestly.
sprint commitmentKeep the phase as a container for a goal. Drop the capacity arithmetic — you are no longer committing a fixed supply of hours.
manual statusAlready refused, and it is the best decision in the codebase. Keep refusing it everywhere the new stages add state.
assignee = a personAn assignment is a lane plus optionally an identity. Putting an agent in a person's slot is what makes every other tool's agent support feel bolted on.
Gantt durationsKeep the dependency graph, discard resource levelling. You cannot schedule a resource you can buy more of mid-sprint.
agent leaderboards“Our AI wrote 60% of the code” rewards volume, which an agent can produce infinitely. Publish survival rate instead — it cannot be gamed by generating more.
LGTM without criteriaApproval and correctness are different signals; Critique separates them for good reason. An approval that does not name what it approved is theatre.
a hosted work databaseThe moment the board lives somewhere the repository does not, it starts drifting from the repository. That is the whole disease.
10Build order

Six phases, and why this order rather than the narrative one

Your vision reads ideation → design → development. The build order is close to the reverse, for two reasons. First, you can hand-write a PRD today but you cannot hand-derive provenance — the later stages depend on the earlier machinery, not the other way round. Second, build the parts nothing else in the field has, first. Ideation surfaces and dependency charts are commodity; a line-level provenance ledger and a spec-conformance reviewer are not.

Provenance

Line-level authorship from harness hooks, and the first two-lane measurements. Nothing else in the plan can be built honestly without it, and it is the only phase with no external precedent to copy from.

10

The reviewer

Three tiers, with tier 1 — does this diff satisfy the criteria it claims? — as the differentiator. Findings that untick, suppressions that live in a diff, and a budget on the reviewer itself. Works in the web app before any extension exists.

Ships  tier 0 deterministic findings · spec-conformance review against the existing packet · finding → untick, via the verify mechanism · per-component learned suppressions · a cap and a ranking on what a human is shown
11

The extension

The second client. Needs 09 to render the gutter and 10 to have findings to render. This is the phase that changes daily behaviour, because it puts all of the above where the work actually happens.

Ships  the three diffs · provenance gutter · findings as comment threads · drift in Problems · CodeLens on the PRD · runs and spend in the status bar · @companion chat participant
12

Design

The architecture-and-schemas stage you asked for, made checkable rather than documented. Mostly a matter of closing loops that are already half-built.

Ships  schema drift against Prisma / DDL / migrations · contract drift · ownership drift for unclaimed source · a design record per feature · the gate that refuses Construction without one
13

Intent

Ideas, bets and appetite, with the falsifiability gate in front of the PRD. Deliberately last of the core five: it is the stage a human can do on paper today, and it is worth designing once you have watched the rest of the pipeline run.

14

Waiting

Dependencies between features, and the critical path weighted by waiting rather than working. The honest successor to the Gantt chart, and the surface that finally shows a manager where the project is actually stuck.

Ships  Requires: parsed from the PRD · the dependency DAG · critical path by decision latency and queue depth · the project-scale view of the attention router
One structural change worth making early, in phase 09. Promote Verify: and the WIP limit into a single gate abstraction before you add the third and fourth gate. Five hard-coded gates will be five different shapes; one abstraction with five instances stays one shape — and it gives you a single place to enforce the rule that a refusal must always name its remedy.
11Risks andopen questions

Where I think this is weakest

Provenance
Accurate only through an instrumented harness. If your team edits substantially outside one, the ledger degrades to inference and the headline feature loses its claim to being a record. Test this early on real usage before building the gutter on top of it.
Review cost
A reviewer that spends more than the work it reviewed is a net loss. Budget it from day one and report its cost next to its findings, so the trade is visible rather than assumed.
Gate friction
Every gate is somewhere a team learns to route around. Each one must earn its refusal, and you should instrument how often each is overridden. A gate overridden 90% of the time is not a gate.
Scale
The event log shards per actor and merges cleanly, but .project is one file — already 48KB at eight phases — and the PRD is one document. At fifty engineers and four hundred features, both become contention points. Worth a plan before it is a problem.
Scope
The model is single-repository. Multi-repo and multi-service organisations are where Backstage-class tools earn their keep, and this design has no answer yet.
The reviewer's floor
Grounding drops findings off the diff — but a genuinely important finding is often off-diff (“this change is fine, but it makes the caller in another file wrong”). The floor is right as a default and needs a deliberate escape hatch.

Two questions only you can answer

  • Is this a product or your team's tool? Everything above works either way, but the answer changes phase 13 completely — a product needs an ideation surface that a non-engineer can use, and an internal tool does not.
  • Single-player or team? The event log and merge driver are built for teams, but every surface today assumes one person at a terminal. Deciding this determines whether phase 11 needs presence, assignment and notification at all.
